# SSR agent instructions

Canonical instructions for this independent repository and descendants. Read the local README and architecture guide before changing implementation.

- Preserve existing source branches, changes and public module identities. No commit, push, reset, publication or deployment without explicit authorization.
- Use English for first-party documentation and explanatory text; preserve executable identifiers and generated/vendor content.
- Keep repository content portable: never write a developer's checkout, home, temporary-toolchain or agent-runtime path into documentation, instructions, code, fixtures or versioned evidence. Use repository-relative paths, documented variables or neutral placeholders.
- Explain SSR responsibilities separately from browser rendering, framework adapters and server hosting. Source inspection is not runtime verification.
- Preserve Beyond module authoring, bare public imports and familiar composed objects. Internal source files are not automatically public modules.
- Keep documentation autonomous and relative links inside this repository. Other components are optional references, not assumed sibling directories.
- Validate links and formatting for documentation; do not run unrelated builds/services or alter executable behavior for a documentation task.
- Test the public contract of every Beyond package or module you implement or change, its error and recovery cases included, following the Beyond testing conventions: Node's own test runner, one process per file; the bare specifier a consumer imports, never a source file or a relative path into a module; promises, events and readiness awaited rather than time, with a bounded wait that fails instead of hanging; whatever a test creates removed with `t.after`, on failure as well; temporary, unique directories and allocated ports; every case asserting its outcome, an error path by its code. A package that the Packages development service compiles is tested with `beyond test`; one that another compiler serves runs its `node:test` files against the modules that compiler serves. Existing suites adopt the conventions when they are changed.
- Keep tests discoverable and their examples readable, as [the testing guide](docs/testing.md) describes for this repository: it names each test level, its command, prerequisites, fixtures and what a pass establishes. Contract/unit and integration tests live in `test/` or `tests/`, complete journeys in `acceptance/`, harness infrastructure in `support/`. Applications, packages, modules and documents a test exercises are checked-in files with their real extensions under the consuming area's `fixtures/`, each group with a README naming its entry modules and expected behavior; the harness copies them to a unique temporary directory, substitutes only explicit values such as versions or ports, and never writes the originals, even on failure. Keep inline only small input values, short edits and protocol payloads; generate source only when generation is the behavior under test (size, combinations, malformed input), with the reason and how to reproduce and inspect it in the guide. Fixtures stay out of production compilation and packaging, and migrating a test keeps its positive, negative and recovery cases and its real execution path.
- Follow the [coding standards](docs/coding-standards.md); they are binding for new and modified code. Source files target 300 lines or fewer and must not exceed 400. Model each responsibility as a class that owns `#private` state and exposes simply named members, composed from collaborating objects. Avoid compound names in methods, properties, variables and parameters by giving the responsibility its own object: `client.register()`, not `registerClient()`. Compound names remain allowed in class definitions. Preserve public contracts, and do not rewrite untouched files only to comply.

Documentation follows [the local documentation standards](docs/AGENTS.md).

The coordinated working branch is `feature/next`. Its base preserves the selected TypeScript implementation; do not switch back to historical source branches for ordinary work.
